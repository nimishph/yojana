yojana: plans as checkable contracts

Plain Markdown plans backed by an append-only log of every requirement revision. It catches conflicting edits, checks claims against the code, and reads progress from beads.

repo: yojana/epic: yoj-9fe (closed)204 testssource: docs/design.md

Why #why

Each cntxt-labs tool owns one layer of an agent's working context. Plans were the layer with no owner.

ToolLayerAnswers

OpenSpec is the closest existing tool. It has no answer for abandoned changes, two changes editing the same requirement, or specs that drift from the code. Yojana covers those three.

Principles #principles

  1. Not a VCS. Git versions files. Yojana versions meaning: which requirement changed, from which base revision, in which change, and why.
  2. Requirement-level revisions. Each requirement has a stable id. Its revision hashes its title, text and claims: r_ plus 16 hex characters.
  3. The log is the source of truth. Plan files are where you edit; every state is rebuilt by folding the log. Same pattern as medha's episode log, duplicated rather than shared until it proves itself in both.
  4. Report, then refuse ambiguity. A conflict, a stale edit or an unverifiable claim is reported and refused or flagged, never resolved silently.
  5. Markdown is edited, HTML is reviewed. People and agents edit plain Markdown. Review happens in a rendered page with comments anchored to requirement revisions.

Plan files #format

Markdown with YAML frontmatter. Requirements are ## headings with an explicit id. Claims go in fenced yojana:claim blocks, which show as code on GitHub and parse without a JavaScript compiler. A file with unresolved git conflict markers is refused.

---
id: plan/plugin-packaging
status: accepted        # draft | accepted | in-progress | realized | superseded | abandoned
beads: [anv-yp2]
---
## Requirement: the core never depends on the CLI {#req-core-no-cli}
Packaging work must not make core/ reach into cli/.

```yojana:claim
kind: wql
expression: //import[contains(@name, "cli/src")] in core/
expect: false
```

Claims #claims

A claim holds when "something matches" equals expect (default true), is violated otherwise, and is unverifiable when the check cannot run. Unverifiable never counts as holding; check --strict makes it fail.

kindexpressionmatches when
patha path or globa file exists
wql<wql> [in <dir>]anvesa's query matches, only under the folder if given
dependents<path> [from <dir>]something imports the path, only importers under the folder if given
text<regex> in <path or glob>a line in those files matches; no file to search is unverifiable

Scoped evidence also states how many matched overall, so a pass that is only true because nothing matches anywhere is visible. That is how a vacuous claim was caught during testing. Prefer claims that name the work: a crate's Cargo.toml exists before its SIMD code does; //function[@name="batch_scan_top_k"] in crates/ holds only once it is written.

Keeping files and log in step #ingest

yojana ingest keeps a base per plan, the revision of each requirement the last time file and log agreed, much like git's index. Each requirement and the plan's status are compared three ways:

file · base · logmeaningingest does
file = login stepnothing
base = log, file differsyou edited itrecords it on top of the log
file = base, log differsthe log movedreports the file as behind
all three differboth movedrefuses the whole file

yojana refresh goes the other way: it rewrites only the requirements a file is behind on, which still match their base, so nothing is lost and your un-ingested edits stay.

Changes and conflicts #changes

Change files use ## ADDED, ## MODIFIED and ## REMOVED Requirement: sections. Opening pins each edit to the requirement's current revision. Archiving applies the change only if nothing it edits has moved since:

Real output from the anvesa test: two changes competed over how the plugin starts its server; the first archived, the second was refused by name and then abandoned with a reason.

draft→ accepted→ in-progress→ realized or superseded abandoned

Branches and merges #merges

The log and bases are committed with the plans and hold one fact per line. Yojana writes .yojana/.gitattributes so git merges them by keeping both sides' lines. Events carry a content id and no stored position, so a merged log reads as one log.

  • Different requirements edited on two branches merge with no manual step.
  • The same requirement edited on both becomes contested. The plan file has an ordinary git conflict; once resolved, ingest records the file's version as the resolution and the collision drops out of status.

Status #status

yojana status [--check] shows each plan's lifecycle, progress from its beads (an epic counts its children; an unreachable bd is reported, never shown as 0%), edits not yet ingested, requirements behind the log, contested requirements, open changes with age, and claim results.

A requirement can name its beads on its heading, {#req-primer beads=anv-35b}. Status then flags close? when every claim holds but a linked bead is open, and reopen? when its beads are closed but a claim is violated. On anvesa's roadmap that produced six close? prompts.

Commands #commands

yojana ingest [--trust-file]              record edits to plan files
yojana change open <file>                 open a change against the log
yojana changes [--all]                    list changes
yojana archive <change>                   apply a change if nothing it edits moved
yojana abandon <change> --reason <text>   close a change without applying it
yojana refresh                            bring log changes into files that fell behind
yojana status [plan] [--check]            the one view
yojana check [plan] [--strict]            verify claims against the code
yojana repair                             recover a corrupt log
yojana comment <plan> <req> "<text>"      note on a requirement (--quote, --reply)
yojana review [plan] [--check]            HTML review page in .yojana/review/
yojana import <file> --id <plan-id>       start a plan from an existing Markdown roadmap

Every command takes --json, errors included. Exit codes: 0 done, 1 refused, violated, invalid or failed, 2 usage.
